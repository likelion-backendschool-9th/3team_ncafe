# 인증 1단계 — 회원 도메인과 비밀번호 저장

작업 브랜치: `feature/session-auth-step1` · 통합 대상: `feature/session-auth`

## 구현 범위

0단계에서 확정한 회원 데이터와 입력 규칙을 코드로 만들고, 실제 PostgreSQL에서 저장·조회·중복 제약을 검증한다. 웹 Security 필터와 회원가입·로그인·로그아웃 API는 이후 단계에서 구현한다.

| 구성 | 역할 |
| --- | --- |
| `entity/user/User` | 고객 회원 생성, 이메일·이름 정규화, 해시 보관, 생성·수정 시각 |
| `UserFields` | 공통 이메일 정규화·입력 제한·저장할 해시 형식 검사 |
| `UserRole`, `UserStatus` | Java에서는 타입으로 구별하고 DB·JSON에는 소문자로 표현 |
| `UserRepository` | 회원 저장·ID 조회와 정규화 이메일 조회·존재 확인 |
| `config/PasswordConfig` | BCrypt 기반 `DelegatingPasswordEncoder` Bean |
| `common/security/Passwords` | 비밀번호 정책 검사, 해시 생성·일치 확인 |

`spring-security-crypto`만 추가했으므로 이번 단계에서는 웹 인증 필터를 등록하지 않는다.

## 회원 생성과 조회

```java
String passwordHash = passwords.encode(rawPassword);
User user = User.createCustomer(name, email, passwordHash);
userRepository.save(user);

String normalizedEmail = UserFields.normalizeEmail(email);
userRepository.findByEmail(normalizedEmail);
```

- 생성 팩터리는 고객·활성 상태를 고정한다. 요청에서 역할·상태를 전달하는 생성 경로는 만들지 않는다.
- 이메일은 `strip()`과 `Locale.ROOT` 소문자 정규화 후 형식과 최대 254자를 검사한다. 조회 전에도 같은 공통 함수를 사용한다.
- 이름은 `strip()` 후 Unicode 코드 포인트 기준 2~50자를 검사한다. UTF-16 길이를 기준으로 하는 `@Size`만으로 대체하지 않는다.
- 이메일 정규화 함수는 잘못된 이메일에 `IllegalArgumentException`을 발생시킨다. 이후 로그인 구현에서는 이를 공통 인증 실패로 변환하고 `500`으로 노출하지 않는다.
- 비밀번호 원문을 Entity에 전달하지 않는다. 고객 생성 팩터리는 `{bcrypt}` 식별자와 유효한 BCrypt 형식의 해시만 받는다.
- Entity에는 공개 setter나 필드를 출력하는 `toString`을 추가하지 않는다. `passwordHash`는 `@JsonIgnore`로 JSON에서 제외한다. 실제 API 응답은 2단계의 DTO를 사용한다.

## 비밀번호 정책

- 최소 8 Unicode 코드 포인트, UTF-8 최대 72바이트다. 한글·이모지의 바이트 수를 기준으로 상한을 적용한다.
- 앞뒤 공백을 포함한 원문을 그대로 해시한다. 잘못된 UTF-16 surrogate 문자열은 UTF-8 변환 중 대체 문자로 바뀌는 것을 막기 위해 거부한다.
- 저장 형식은 `{bcrypt}` 접두사가 있는 단방향 해시이며 매번 다른 salt를 사용한다.
- `matches`는 입력 정책 위반, 비밀번호 불일치, 지원하지 않는 형식·손상된 해시를 `false`로 처리한다. 원문·해시를 오류 메시지나 로그에 직접 넣지 않는다.
- 가입과 로그인은 같은 `PasswordEncoder`를 주입받는다. Spring Security의 [공식 비밀번호 저장 방식](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)을 따른다.

## DB 계약

- `users`의 ID는 IDENTITY 방식, 이메일은 `uk_users_email` 유니크 제약, 필수 컬럼은 NOT NULL로 매핑한다.
- `role/status`는 JPA의 `@EnumeratedValue`로 `customer/admin`, `active/suspended`를 저장한다. Hibernate가 생성한 DB check 제약으로 그 외 값을 거부한다.
- `password_hash`는 인코딩 식별자를 포함할 수 있도록 길이 100으로 정의한다. 비밀번호 원문 컬럼은 없다.
- 생성 시 `created_at/updated_at`을 함께 설정한다. 두 컬럼은 `TIMESTAMPTZ`이며 변경 시각 갱신 콜백도 둔다. 프로필 수정 기능은 후속 범위다.

## 검증

기존 [0단계 테스트 격리](2026-10-22-auth-step0.md#테스트-실행과-db-격리)를 유지한다. 개발 DB의 스키마·데이터를 변경하지 않고 컨테이너 DB에만 테스트 회원을 저장한다.

- 단위 테스트: 고객·활성 상태, 이메일 정규화와 기본 locale 독립성, 잘못된 입력, 이름 코드 포인트 경계, 해시·JSON 비노출
- 비밀번호 테스트: ASCII·한글·이모지의 길이/바이트 경계, 공백 보존, salt 차이, 잘못된 입력과 손상된 해시 거부
- PostgreSQL: 실제 회원 저장·조회, 생성 시각·초기 수정 시각, 소문자 역할·상태, 해시 일치, 정규화 이메일 중복과 enum check 제약
- 직렬화: 실제 Spring의 Jackson Bean으로도 원문·해시가 노출되지 않음 확인
- 결과: `./gradlew check`에서 단위 테스트 96개 + PostgreSQL 통합 테스트 5개, 총 **101개 통과**. 실패·오류·생략 없음
- 검토 중 발견한 손상된 BCrypt 해시의 예외 처리를 보완하고 해당 회귀 테스트를 포함해 재검증 완료

다음은 `feature/session-auth-step2`의 Security·CSRF·회원가입 API 구현이다.
