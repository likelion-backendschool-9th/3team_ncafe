# 인증 5단계 — 기존 API 권한·통합 검증

작성일: 2026-10-25 · 작업 브랜치: `feature/session-auth-step5`

## 구현 범위

현재 구현된 API의 접근 정책을 확정하고, 실제 쿠키·로그인·PostgreSQL과 함께 기존 메뉴·카테고리 기능을 검증한다. 데이터베이스를 유지한 애플리케이션 재시작에서 회원 데이터 보존과 메모리 인증 세션 폐기도 확인한다. 프론트 연결과 공개 메뉴 조회 API의 신규 개발은 이번 단계에 포함하지 않는다.

3·4단계 PR이 미병합 상태이므로 검증한 `feature/session-auth-step4`에서 분기했다. 후속 초안 PR의 대상도 우선 해당 브랜치다. 앞 단계들을 `feature/session-auth`에 먼저 통합한 뒤 5단계 커밋을 최신 통합 브랜치 위로 rebase하고 PR 대상을 변경한다. 후속 PR을 앞 단계 브랜치로 먼저 머지하지 않는다. rebase 충돌은 abort 후 보고한다.

## 접근 정책

실제 MVC 매핑 13개와 로그인·로그아웃 필터 2개를 확인했다. 아래 경로는 모두 `/api/v1` 기준이다. 변경 요청에는 세션 쿠키와 유효한 CSRF 토큰이 필요하다.

| 경로 | 메서드 | 권한 |
| --- | --- | --- |
| `/auth/csrf` | GET | 익명 허용 |
| `/auth/signup` | POST | 익명 허용, 가입만 수행 |
| `/auth/login` | POST | 익명 허용, 표준 인증 필터 |
| `/auth/logout` | POST | 익명 허용, 표준 로그아웃 필터 |
| `/my` | GET | 활성 고객·관리자 본인 |
| `/admin/menus` | GET, POST | 관리자 |
| `/admin/menus/{id}` | GET, PUT, DELETE | 관리자 |
| `/admin/categories` | GET, POST | 관리자 |
| `/admin/categories/{id}` | PUT, DELETE | 관리자 |
| `/admin/categories/order` | PUT | 관리자 |

기존 관리자 네임스페이스는 `ADMIN` 권한을 유지하고, `GET /api/v1/my`의 인증 요구를 명시했다. 나머지는 `denyAll`이다. 새 업무 Controller를 추가할 때는 접근 정책도 함께 선언해야 한다. 현재 공개 메뉴·카테고리 조회 Controller는 없다.

로그인·로그아웃 이후 CSRF 재조회, 정지·삭제·역할 갱신 등 앞 단계 정책은 유지한다. 공개 가입은 `customer/active`만 생성한다. 통합 테스트의 관리자는 독립 테스트 DB에 fixture로 만들며 운영 계정을 자동 생성하거나 공개 가입의 관리자 선택을 허용하지 않는다.

## 오류와 메서드 구분

- 보호된 조회는 익명 `401 UNAUTHENTICATED`, 권한이 부족한 회원 `403 FORBIDDEN`이다.
- CSRF 누락·불일치인 변경 요청은 권한 판정보다 먼저 `403 CSRF_INVALID`다. 역할 거부 검증에는 유효한 CSRF를 붙인다.
- 정책에 없는 경로·메서드는 익명 `401`, 인증된 회원·관리자는 `403`이다. `GET /api/v1/auth/logout`도 인증 상태에서 `403`이며 세션은 유지한다.
- 관리자 네임스페이스에서 관리자 권한 검사를 통과한 후 대상이 없으면 `404`, 기존 Controller가 지원하지 않는 메서드이면 `405`가 될 수 있다. 정상 권한의 업무 입력 오류 `400`, 충돌 `409`도 유지한다.
- CSRF·본인 조회의 공개/인증 허용은 정확한 GET에 적용한다. HEAD 등을 자동으로 공개하지 않는다.
- 허용 origin의 CORS preflight는 인증 전에 처리한다. 이는 실제 업무 요청의 접근 허용과 별개다.
- 서버의 ERROR dispatcher 허용은 에러 응답을 위한 기존 설정이다. 일반 HTTP 요청으로 `/error`나 미지정 업무 경로를 공개하지 않는다.

## 통합 검증

`cd backend && ./gradlew check` 통과: 단위·Security 테스트 **178개**, PostgreSQL·실제 HTTP 통합 테스트 **56개**, 총 **234개**. 실패·오류·생략 없음. 개발 `.env`와 SQL 초기화를 제외한 Testcontainers PostgreSQL을 사용했다.

`AdminSessionIntegrationTest`는 실제 브라우저 역할의 HTTP 클라이언트로 가입 → 로그인 → 본인 조회 → 로그아웃을 연결한다. 별도 테스트 관리자도 표준 로그인을 거친 후 카테고리 생성·이름/순서 변경·삭제, 메뉴 생성·목록/상세·수정·삭제를 수행한다. 카테고리 삭제 시 메뉴가 기본 카테고리로 이동하고 메뉴 삭제는 기존 보관 처리로 반영되는지도 확인한다.

`ApiAccessPolicyTest`는 실제 Security 필터에서 경로·메서드 경계를 검증한다. 테스트 전용 Controller를 실제로 추가해도 접근 규칙이 없으면 고객·관리자 모두 진입하지 못하는지 확인한다.

`AuthenticationRestartIntegrationTest`는 한 PostgreSQL 컨테이너와 브라우저 쿠키를 유지하며 실제 `BackendApplication` 컨텍스트만 순차적으로 종료·기동한다. 두 기동 모두 테스트 DB URL·catalog를 확인하며, 스키마는 `update`로 데이터가 남게 한다. 재시작 후 회원 ID·동일 해시·비밀번호 검증이 유지되고, 이전 쿠키·CSRF는 거부되며 새 로그인은 성공해야 한다. DB 서버 재시작이나 실제 운영 배포 환경까지 검증하는 테스트는 아니다.

기존 동시 이메일 가입 테스트도 전체 check에 포함해 통과했다. 같은 정규화 이메일의 동시 요청은 한 건만 생성하고 나머지는 `409`임을 확인했다. CSRF·회원 상태·역할 변경·운영 쿠키·유휴 만료의 앞 단계 회귀 검사도 함께 통과했다.

정책 구성은 [Spring Security 요청 권한 문서](https://docs.spring.io/spring-security/reference/servlet/authorization/authorize-http-requests.html)를 기준으로 한다.

다음은 6단계 프론트 연결이다. 사용자의 다음 요청 후 별도로 진행하고, 모든 단계 PR의 머지는 사람이 한다.
