# 인증 0단계 — 계약과 실행 기준

통합 브랜치: `feature/session-auth` · 작업 브랜치: `feature/session-auth-step0`

## 이번 단계의 결과물

인증 구현을 시작하기 전에 API·입력·세션 정책을 확정하고, 기존 테스트와 실제 PostgreSQL 연결을 서로 구분해 검증한다. 회원 도메인이나 인증 필터는 아직 추가하지 않는다. 구현 계약은 [인증 청사진 3~4장](2026-10-22-auth-blueprint.md#3-확정한-구현-기준)을 따른다.

| 단계 | 브랜치 | 작업 |
| --- | --- | --- |
| 0 | `feature/session-auth-step0` | 계약 확정, 실행 환경 및 DB 격리 검증 |
| 1 | `feature/session-auth-step1` | 회원 도메인, 이메일 정규화, 비밀번호 해시 |
| 2 | `feature/session-auth-step2` | Security, CSRF, 회원가입 |
| 3 | `feature/session-auth-step3` | 로그인, 현재 회원 조회 |
| 4 | `feature/session-auth-step4` | 로그아웃, 만료, 기존 세션의 회원 상태 확인 |
| 5 | `feature/session-auth-step5` | 기존 API 권한, 통합 검증 |
| 6 | `feature/session-auth-step6` | 프론트 목 인증 교체 및 브라우저 검증 |

각 브랜치는 해당 단계 착수 시 최신 통합 브랜치에서 만든다. 선행 단계가 통합되기 전에 다음 단계 구현을 시작하지 않는다. 이번 요청에 따라 단계 PR은 에이전트가 `feature/session-auth`에 통합하지만 최종 `develop` PR은 사람이 머지한다.

## 확정한 계약

- 이메일로 로그인한다. 이메일은 앞뒤 공백 제거와 `Locale.ROOT` 소문자 정규화 후 유일해야 하고 최대 254자다.
- 이름은 앞뒤 공백 제거 후 Unicode 코드 포인트 기준 2~50자다.
- 비밀번호는 코드 포인트 기준 최소 8자이며 UTF-8 최대 72바이트다. 비밀번호의 공백은 제거하지 않는다.
- 공개 가입은 활성 고객만 생성한다. API 자체는 로그인시키지 않고, 프론트는 가입 성공 뒤 로그인 API를 호출해 현재 UX를 유지한다.
- 로그인은 form-urlencoded 이메일·비밀번호와 CSRF 토큰을 사용하고, 표준 Spring Security 인증 필터로 처리한다.
- 세션은 필요할 때 생성하고 30분 유휴 만료를 사용한다. 로그인 시 ID를 바꾸며 로그아웃은 요청한 세션만 무효화한다.
- 세션 쿠키는 HttpOnly, Path=/, SameSite=Lax이며 운영 HTTPS에서 Secure를 사용한다.
- CSRF 조회, 로그인·가입·로그아웃, 현재 회원 조회 경로와 JSON 응답·오류는 청사진 4장을 따른다.

이 기준의 실제 검증 코드는 각 구현 단계에서 추가한다. 0단계 테스트 통과를 인증 기능 완성으로 간주하지 않는다.

## 개발 실행 환경

빌드는 추적 중인 `backend/build.gradle`·`settings.gradle`을 기준으로 한다. Java 21과 Gradle Wrapper 8.14.5를 사용하며, 개발 DB는 PostgreSQL 16에서 연결을 확인했다.

`backend/.env`에는 다음 세 키를 실제 개발 접속 정보로 설정한다. 값은 커밋하거나 테스트 설정에 복사하지 않는다.

```dotenv
DB_URL=jdbc:postgresql://localhost:5432/ncafe_dev
DB_USERNAME=개발_DB_계정
DB_PASSWORD=개발_DB_비밀번호
```

위 호스트·포트·DB명은 로컬 예시이며 실제 DB 환경에 맞춰 바꾼다. `KEY=value` 형식으로 따옴표·`export` 없이 작성한다. `.gitignore`의 `.env` 규칙은 `backend/.env`도 제외한다.

프로젝트 최상위에서 다음과 같이 실행한다.

```bash
cd backend
./gradlew --version
./gradlew test
./gradlew bootRun
```

Spring의 `.env` 가져오기 경로는 실행 디렉터리에 상대적이므로 `backend`에서 실행한다. IDE로 실행할 때도 working directory와 envFile 위치를 `backend`에 맞춘다. 기존 사용자 IDE 설정은 이번 변경에서 덮어쓰지 않는다.

`bootRun`은 개발 DB의 스키마와 기본 카테고리를 생성·갱신할 수 있다. 이번 개발 DB 연결 점검에서는 애플리케이션을 띄우지 않고 `default_transaction_read_only=on`인 연결에서 `SELECT 1`과 연결 대상·서버 버전만 확인했다.

## 테스트 실행과 DB 격리

기존 `src/test`의 50개 테스트는 mock·standalone MockMvc·Hibernate 메타데이터 검사다. 실제 DB 연결 성공을 증명하지 않으므로 테스트를 두 종류로 나눈다.

| 명령 (`backend/`에서 실행) | 검증 범위 | Docker |
| --- | --- | --- |
| `./gradlew test` | 기존 단위·Controller·메타데이터 검사 | 불필요 |
| `./gradlew integrationTest` | 실제 PostgreSQL에서 Spring 애플리케이션 시작 및 datasource 격리 | 필요 |
| `./gradlew check` | 위 두 작업을 포함하는 전체 검증 | 필요 |

Docker를 실행한 뒤 통합 테스트를 수행한다. 최초 실행 시 공식 `postgres:16-alpine` 이미지와 Testcontainers 보조 이미지를 내려받을 수 있다.

- `src/integrationTest`는 별도 source set이며 테스트 라이브러리는 Boot 관리 버전을 사용한다.
- 테스트 컨텍스트의 PostgreSQL 컨테이너는 `ncafe_test` DB와 테스트 전용 계정을 사용하고 임의 포트를 배정받는다. 개발 DB의 계정·볼륨을 공유하지 않고 컨테이너를 재사용하지 않는다.
- Spring이 컨테이너를 Bean으로 관리하고 `@ServiceConnection`의 `JdbcConnectionDetails`가 datasource의 URL·사용자·비밀번호 **세 값 모두**를 컨테이너 값으로 제공한다. 연결 설정 프로퍼티보다 우선한다.
- 컨테이너는 의존하는 Bean보다 먼저 시작하고, JPA 스키마 정리와 커넥션 풀 종료가 끝난 뒤 중지한다. DB가 먼저 닫혀 종료 시 연결 오류가 나는 문제도 방지한다.
- 통합 테스트에서는 `.env` import와 `data.sql` 자동 실행을 끈다. `create-drop`은 이 컨테이너의 스키마에만 적용한다.
- 테스트는 실제 연결이 PostgreSQL이고 DB명이 `ncafe_test`이며 JDBC URL이 컨테이너 URL과 같은지 검사한다. 애플리케이션의 기본 `기타` 카테고리 초기화도 확인한다.
- Docker가 없거나 컨테이너 시작에 실패하면 통합 테스트가 실패한다. 개발 DB로 대체하거나 테스트를 성공으로 건너뛰지 않는다.
- `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`에 개발 값이 있어도 통합 테스트 연결에 사용하지 않는다. 테스트 SQL 초기화 설정을 개발 `application.yml`에 추가하지 않는다.

Testcontainers는 실제 의존 서비스를 Docker로 격리해 시험하기 위한 도구다. [Spring Boot 공식 안내](https://docs.spring.io/spring-boot/reference/testing/testcontainers.html), [PostgreSQL 모듈](https://java.testcontainers.org/modules/databases/postgres/)

## 검증 기록

- Java: Temurin 21.0.11, Gradle Wrapper: 8.14.5
- 개발 DB: 기존 `.env`의 PostgreSQL 16에 읽기 전용 연결 성공, `SELECT 1` 정상, 설정한 DB와 실제 연결 대상 일치
- `./gradlew clean check`: 기존 테스트 50개 + PostgreSQL 통합 테스트 1개, 총 51개 통과. 실패·오류·생략 없음
- 통합 테스트: 실제 PostgreSQL 연결·`ncafe_test` DB명·컨테이너 JDBC URL 일치 및 `기타` 카테고리 초기화 확인
- 종료 순서: JPA의 테스트 스키마 정리 → 커넥션 풀 종료 → 컨테이너 중지. 종료 시 DB 연결 오류 없음
- 문서 상대 링크·코드 블록과 `git diff --check` 확인
