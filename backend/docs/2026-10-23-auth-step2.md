# 인증 2단계 — Security·CSRF·회원가입

작성일: 2026-10-23 · 작업 브랜치: `feature/session-auth-step2` · 통합 대상: `feature/session-auth`

## 구현 범위

Spring Security 필터를 적용하고 익명 세션의 CSRF 발급 → 회원가입 → PostgreSQL 저장 흐름을 연결한다. 기존 관리자 API도 관리자 권한과 CSRF 검사를 거쳐야 한다. 가입 성공은 계정 생성이며 로그인은 3단계에서 구현한다.

| 구성 | 담당 |
| --- | --- |
| `SecurityConfig` | 경로·메서드별 접근 제어, 세션·CSRF·CORS 정책 |
| `SecurityErrorHandler` | 인증·권한·CSRF 실패를 기존 `{code,message}` JSON으로 응답 |
| `AuthController` | CSRF 조회와 회원가입 HTTP 요청·응답 |
| `AuthService` | 입력 검증, 중복 검사, 해시 생성, 고객 계정 저장 트랜잭션 |
| `SignupRequest/Response`, `CsrfResponse` | 필요한 입력·공개 응답 필드만 표현 |

Boot 관리 `starter-security`, `starter-security-test`를 사용하고 별도 crypto 선언은 정리했다. 관리자 Controller 테스트는 standalone MockMvc에서 실제 필터를 포함하는 `@WebMvcTest`로 전환했다.

## API와 호출 순서

1. `GET /api/v1/auth/csrf`를 호출해 `200` JSON의 `headerName`, `parameterName`, `token`과 `JSESSIONID` 쿠키를 받는다.
2. 같은 쿠키와 `X-CSRF-TOKEN` 헤더를 포함해 `POST /api/v1/auth/signup`을 JSON으로 보낸다.
3. 정상 입력이면 `201`과 `{id,name,email,role,status}`를 반환한다. DB에는 해시만 저장하고 세션은 로그인시키지 않는다.

```json
{
  "name": "단골 고객",
  "email": "member@example.com",
  "password": "example-password",
  "passwordConfirm": "example-password"
}
```

CSRF 토큰 발급과 가입 응답은 `Cache-Control: no-store`다. 브라우저가 다른 포트의 백엔드로 호출할 때는 `credentials: "include"`를 사용한다. CSRF 토큰은 조회 중 실제로 읽어 익명 세션에 저장하며, 쿠키가 있어도 인증되었다는 뜻은 아니다.

| 상황 | 응답 |
| --- | --- |
| 정상 가입 | `201`, 활성 고객 정보 |
| 입력 제한 위반·확인 비밀번호 불일치 | `400 VALIDATION_ERROR` |
| 잘못된 JSON·JSON null | `400 INVALID_REQUEST` |
| 정규화 이메일 중복 | `409 EMAIL_ALREADY_EXISTS` |
| CSRF 누락·불일치·다른 세션의 토큰 | `403 CSRF_INVALID` |
| 비로그인 상태의 관리자 API 조회 | `401 UNAUTHENTICATED` |
| 고객이 유효한 CSRF로 관리자 API 접근 | `403 FORBIDDEN` |

클라이언트가 `role/status`를 보내도 가입 입력으로 사용하지 않고 `customer/active`를 서버에서 고정한다. 비밀번호 필드는 요청 DTO의 JSON 직렬화와 `toString`에서도 숨긴다. 이름·이메일은 PostgreSQL에서 저장할 수 없는 NUL·잘못된 UTF-16 surrogate도 거부한다.

## 중복 가입과 트랜잭션

`AuthService`는 정규화 이메일의 사전 존재 확인과 DB 유니크 제약을 함께 사용한다. `saveAndFlush`로 저장 오류를 트랜잭션 내부에서 확인하고, Hibernate 예외 원인의 제약 이름이 정확히 `uk_users_email`일 때만 이메일 중복 오류로 바꾼다. 그 외 DB 오류를 이메일 중복으로 오인하지 않는다.

동시에 같은 이메일로 가입하면 한 요청만 커밋하고 나머지는 `409`다. 이 경로는 테스트 전체 트랜잭션에 묶지 않고 실제 HTTP 요청과 DB 커밋으로 검증한다.

## 세션·CORS·환경

- 세션은 `IF_REQUIRED`, 30분 유휴 만료이며 쿠키는 `JSESSIONID`, `HttpOnly`, `Path=/`, `SameSite=Lax`다. 영속 쿠키의 `Max-Age`는 설정하지 않는다.
- 기본 로컬 HTTP 설정은 `Secure=false`이고 `prod` 프로필은 `Secure=true`다. 운영에서는 `SPRING_PROFILES_ACTIVE=prod` 환경변수로 해당 프로필을 활성화한다.
- 허용 origin의 기본값은 `http://localhost:3000`이며 `CORS_ALLOWED_ORIGINS`로 실제 프론트 주소를 설정한다. 여러 값은 쉼표로 구분한다. credentials와 `*` origin 조합은 거부한다.
- CORS preflight를 인증보다 먼저 처리하며, 허용하지 않은 origin에는 CORS 허용 헤더를 반환하지 않는다.
- Basic·기본 로그인 폼·기본 로그아웃·로그인 전 요청 캐시를 사용하지 않는다. 임시 `AuthenticationManager`가 신규 인증을 거부해 Boot의 기본 계정 생성을 막는다. 3단계에서 실제 DB 인증으로 교체한다.
- 익명 접근은 CSRF `GET`, 가입·로그인 경로의 `POST`만 허용한다. 로그인 처리는 아직 없고, 기존 관리자 경로는 `ADMIN` 권한을 요구한다. 나머지 경로는 인증을 요구한다.
- 인증·권한·CSRF 오류는 로그인 화면으로 이동하거나 Basic 인증 팝업을 유도하지 않고 JSON으로 응답한다.

CSRF 및 CORS 구현은 [Spring Security CSRF 문서](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)와 [CORS 문서](https://docs.spring.io/spring-security/reference/servlet/integrations/cors.html)를 기준으로 한다.

## 검증

기존 [테스트 격리 기반](2026-10-22-auth-step0.md#테스트-실행과-db-격리)을 유지하고 실제 개발 DB는 변경하지 않았다.

- 서비스: 입력·확인 비밀번호·사전 중복·DB 중복 경쟁·관련 없는 DB 제약의 예외 처리, DTO 비밀번호 비노출
- 관리자 API: 실제 Security 필터에서 관리자 정상 동작, 익명 `401`, 고객 `403`, CSRF 누락 `403`과 저장소 미호출
- 기본 인증: 생성된 UserDetailsService 없음, Basic 요청 실패, 인증 팝업·리다이렉트 헤더 없음
- 실제 HTTP: 쿠키·토큰 발급, 가입 저장·해시·고객 권한, 가입 후 비로그인 유지, CSRF 오류의 DB 저장 방지
- 경쟁 상태: 두 클라이언트의 동시 가입에서 `201/409` 및 DB 한 건 저장
- 환경: 실제 CORS preflight, 로컬 쿠키 속성과 운영 `prod` 프로필의 Secure 쿠키
- 결과: `./gradlew check`에서 단위·Security 필터 테스트 127개 + PostgreSQL·실제 HTTP 통합 테스트 24개, 총 **151개 통과**. 실패·오류·생략 없음
- 검토에서 발견한 이름·이메일의 NUL·잘못된 Unicode 입력을 보완하고 단위 및 HTTP 회귀 테스트까지 재검증 완료
