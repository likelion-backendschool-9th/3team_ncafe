# 인증 6단계 — 프론트 세션 연결

작성일: 2026-10-25 · 작업 브랜치: `feature/session-auth-step6`

## 구현 범위

`/login`·`/signup` ↔ Auth와 `/my` ↔ my/Users를 실제 백엔드 인증에 연결했다. 공개 인증 액션과 기존 Server Actions를 유지하고 브라우저·SSR·백엔드가 같은 JSESSIONID를 사용한다. 목 회원 데이터와 서명 쿠키로 로그인 상태를 만들지 않는다.

선행 3~5단계 PR이 미병합일 때 검증한 `feature/session-auth-step5`에서 분기해 후속 초안 PR을 만들었다. 2026-10-25 사용자의 명시적 요청으로 이번에 한해 에이전트가 #71 → #72 → #73 → [#74](https://github.com/likelion-backendschool-9th/3team_ncafe/pull/74)를 `feature/session-auth`에 순서대로 squash 병합했다. 각 후속 단계는 앞 단계 통합 후 최신 통합 브랜치 위로 rebase하고 PR 대상을 변경했다. 0~6단계 통합을 완료했으며, 일반적인 사람 머지 규칙은 유지한다.

`develop`에는 반영하지 않았고, `feature/session-auth` → `develop` [#61](https://github.com/likelion-backendschool-9th/3team_ncafe/pull/61)은 열린 초안으로 유지한다.

## 요청·쿠키 흐름

- `app/_lib/api/auth.ts`는 server-only 액션 진입점이다. 요청마다 새 BackendSession을 만들고 브라우저의 백엔드 세션 쿠키만 가져온다. 사용자 간 쿠키 저장소를 공유하지 않는다.
- 변경 전 `GET /api/v1/auth/csrf`를 받아 같은 쿠키·CSRF로 호출한다. 가입은 JSON, 로그인은 폼 인코딩이다. 로그인 후 변경된 세션 쿠키로 새 CSRF를 조회한다.
- 모든 upstream Set-Cookie를 개별 처리하며 Domain·Path·Secure·HttpOnly·SameSite·만료 속성을 유지한다. Expires의 쉼표를 기준으로 헤더를 나누지 않는다. Next 쿠키 파서가 생략하는 `Max-Age=0`도 명시적으로 보존한다.
- 오류 응답의 세션 만료 쿠키도 처리한다. 정지·삭제된 세션의 CSRF 조회에서 인증이 종료되면 새 익명 CSRF로 로그아웃을 마친다.
- `getCurrentUser`는 브라우저 쿠키를 명시해 `GET /api/v1/my`를 `no-store`로 조회한다. React cache는 한 서버 렌더 안에서만 중복 요청을 줄인다. Server Components는 쿠키를 쓰지 않으며 Proxy·액션이 만료 쿠키를 반영한다.
- Proxy는 `/cart`, `/checkout`, `/my/*`, `/admin/*`에서 백엔드 상태·역할을 확인한다. Server Action과 백엔드의 최종 권한 검사도 유지한다.
- 브라우저 직접 API 호출은 `/api/v1/:path*` rewrites로만 중계한다. 기존 TTS·뮤직박스 Next 라우트는 유지한다.

## 화면 동작

- 가입 성공 후 별도 로그인을 호출해 자동 로그인 UX를 유지한다. 가입만 성공했다면 가입 완료 안내와 로그인 화면으로 보내며 가입을 재시도하지 않는다.
- 이름·이메일은 실패 후 유지하고 비밀번호는 action state·응답·브라우저 저장소에 담지 않는다. 오류는 해당 필드와 연결하고 첫 오류에 포커스를 둔다. 처리 중 중복 제출을 막는다.
- 이름 2~50 코드 포인트, 이메일 254자, 비밀번호 8 코드 포인트 이상·UTF-8 72바이트 이하를 확인한다. 최종 검증은 백엔드가 수행한다.
- `next`는 안전한 상대 경로만 허용하며 외부·역슬래시·제어 문자 경로를 거부한다. 기본 이동은 고객 `/`, 관리자 `/admin`이다.
- 회원 ID는 백엔드 숫자 ID를 사용하고 `/my`에 그대로 표시한다. 아직 목인 주문·신청곡 저장소에는 경계에서만 문자열로 변환해 전달한다. 목 회원을 실제 DB로 이관하지 않는다.
- 기존 `ncafe_mock_session`은 읽지 않고 로그인·가입·로그아웃 때 제거한다. 목 기본 계정 안내도 로그인 화면에서 제거했다.
- SessionSync는 임의 변경 알림만 탭 간 전송한다. 회원·토큰 정보는 저장하지 않는다. 다른 탭의 변경, 포커스·가시성 복귀·뒤로 가기에서 서버 인증을 새로 확인한다.

## 환경과 남은 범위

`frontend/.env.local.example`의 서버 전용 `API_ORIGIN`을 실제 백엔드 origin으로 설정한다. 로컬은 호스트를 `localhost`로 통일하고 백엔드 HTTP 쿠키 설정을 사용한다. 운영 HTTPS의 Secure 설정은 백엔드 `prod` 프로필에서 적용하며, 프론트·백엔드에서 유효한 Cookie Domain/Path로 배포해야 한다.

인증 외 메뉴·주문·뮤직박스·관리자 회원 화면은 기존 목 업무 데이터를 유지한다. 이 목 기능은 운영 모드에서 차단된다. 따라서 이번 검증은 로컬 개발 서버의 전체 로그인 이동과 프로덕션 서버의 인증 화면·본인 조회를 확인한 것이며, 나머지 업무 화면의 운영 전환이나 배포는 별도 작업이다. 관리자 회원 목 화면의 상태 변경은 실제 백엔드 계정을 변경하지 않는다.

## 검증

- `npm run lint`, `npm run typecheck`, `npm run build` 통과
- Playwright 11개 통과: 실제 브라우저 8개 + 전송·안전 경로 검사 3개
- 가입→자동 로그인→숫자 회원 조회→새로고침→로그아웃→보호 페이지 차단, 실제 관리자 이동·고객 거부
- 다른 탭 로그아웃·뒤로 가기, 잘못된 로그인·중복 가입·비밀번호 경계 오류, 이름/이메일 유지와 비밀번호 삭제
- HttpOnly·SameSite·Path, JS 세션 쿠키 비노출, rewrites의 CSRF 유지, 다중 Set-Cookie·세션 ID 변경·만료 응답 처리
- 테스트 전용 중계 서버로 가입 성공 후 로그인만 실패시켜 로그인 재시도로 복구 확인
- axe로 로그인·가입·본인 조회 main 영역의 serious/critical 위반 없음. 실제 화면 스크린샷 확인
- 프로덕션 서버에서 Tab·Enter로 가입→자동 로그인→본인 조회 확인
- Lighthouse 접근성: 로그인 100점, 회원가입 100점

브라우저 검증은 독립 PostgreSQL 컨테이너를 사용했고 개발 `.env`와 DB는 변경하지 않았다. 재현 절차는 [프론트 E2E 안내](../../frontend/e2e/README.md)에 정리했다. 백엔드 코드는 5단계의 234개 통과 상태를 유지한다.
