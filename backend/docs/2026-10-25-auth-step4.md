# 인증 4단계 — 로그아웃·만료·회원 상태 검사

작성일: 2026-10-25 · 작업 브랜치: `feature/session-auth-step4`

## 구현 범위

표준 로그아웃으로 요청한 세션을 종료하고 쿠키를 만료시킨다. 기존 인증 세션은 보호 요청의 권한 검사 전에 DB의 최신 회원 상태와 역할을 반영한다. 기존 30분 유휴 만료 정책을 유지하며 실제 서블릿 세션 만료도 검증한다.

3단계 PR이 미병합 상태이므로 검증한 `feature/session-auth-step3`에서 분기했다. 이번 후속 PR도 우선 해당 브랜치를 대상으로 해 4단계 변경만 보여준다. 3단계가 `feature/session-auth`에 머지되면 4단계를 통합 브랜치 위로 rebase하고 PR 대상을 변경한다. 이 PR을 3단계 브랜치에 먼저 머지하지 않는다. rebase 충돌은 임의로 해결하지 않고 abort 후 보고한다.

## 로그아웃 호출

1. 로그인 직후 `GET /api/v1/auth/csrf`로 받은 새 토큰을 준비한다.
2. 로그인 세션 쿠키와 `X-CSRF-TOKEN` 헤더로 `POST /api/v1/auth/logout`을 호출한다. 본문은 필요 없다.
3. 성공하면 본문 없는 `204`, `Cache-Control: no-store`, 세션 쿠키 만료 응답을 받는다.
4. 기존 쿠키로 `/api/v1/my`를 요청하면 `401`이다. 이후 가입·로그인·로그아웃 같은 변경 요청에는 `GET /api/v1/auth/csrf`에서 새 익명 쿠키와 토큰을 받은 뒤 사용한다.

| 조건 | 결과 |
| --- | --- |
| 인증 세션 + 유효한 CSRF | `204`, 요청한 세션 종료 |
| 익명 세션 + 유효한 CSRF | `204`, 익명 세션 종료 |
| 로그인 후 DB에서 정지된 회원 + 아직 유효한 CSRF로 로그아웃 | `204` |
| CSRF 누락·불일치·다른 세션 토큰 | `403 CSRF_INVALID`, 로그아웃하지 않음 |
| `GET /api/v1/auth/logout` | 로그아웃하지 않음 |
| 종료·만료된 세션의 CSRF로 변경 요청 | `403 CSRF_INVALID` |

로그아웃 Controller를 추가하지 않는다. `LogoutFilter`가 `SecurityContextLogoutHandler`와 CSRF 정리 핸들러를 실행하고, `SessionCookieLogoutHandler`는 실제 세션 쿠키의 이름·Path·Domain으로 `Max-Age=0`을 보낸다. 로컬·운영의 HttpOnly·Secure·SameSite 설정도 반영한다. `ApiLogoutSuccessHandler`가 리다이렉트 없는 `204`를 반환한다.

여러 기기로 로그인한 경우 요청한 세션만 종료한다. 모든 기기의 세션을 한 번에 종료하는 기능은 이번 범위에 포함하지 않는다.

## 기존 인증 세션 검사

`SessionMemberFilter`는 컨테이너 필터로 중복 등록하지 않고 Security 체인에만 추가한다. 순서는 인증 복원·CSRF 검사·로그아웃 처리 후, `AuthorizationFilter` 전이다. 따라서 로그아웃을 먼저 처리하고 나머지 인증 요청에는 DB 상태를 확인한다.

| DB 조회 결과 | 현재 요청 | 이후 요청 |
| --- | --- | --- |
| 활성 회원 | 최신 정보·역할의 principal과 권한으로 검사 | 갱신된 인증 유지 |
| 정지 회원 | `403 FORBIDDEN`, 세션·인증·쿠키 정리 | 기존 쿠키로 인증 불가, `401` |
| 삭제된 회원 | `401 UNAUTHENTICATED`, 세션·인증·쿠키 정리 | 기존 쿠키로 인증 불가, `401` |

예상한 principal 형식이 아닌 인증도 `401`로 차단한다. 역할은 세션에 남은 예전 값으로 판단하지 않는다. DB에서 관리자를 고객으로 변경하면 다음 관리자 요청부터 `403`이며, 고객을 관리자로 변경하면 다음 요청부터 관리자 권한이 반영된다.

`SessionMemberService`가 읽기 전용 트랜잭션에서 현재 회원을 조회하고, `SessionUserDetails.forSession`으로 해시가 없는 principal을 만든다. 요청마다 새 인증·SecurityContext를 만들고 로그인과 같은 저장소에 저장한다. 로그인에는 기존 CSRF 세션이 필수이므로 저장소의 새 세션 생성은 허용하지 않는다. 회원 조회 도중 다른 요청이 세션을 종료하더라도 인증 세션을 다시 만들지 않는다. 이미 진행 중인 요청까지 취소하는 기능은 아니다.

## 만료

운영 설정은 30분 유휴 만료와 세션 쿠키를 유지한다. 세션이 만료되면 서버 인증·CSRF가 없어지므로 쿠키가 남아 있어도 재인증해야 한다. 위조한 세션 ID나 로그아웃 이전 쿠키도 인증에 사용할 수 없다.

## 검증

`cd backend && ./gradlew check` 통과: 단위·Security 테스트 **166개**, PostgreSQL·실제 HTTP 통합 테스트 **51개**, 총 **217개**. 실패·오류·생략 없음. PostgreSQL은 기존 Testcontainers 격리를 사용했고 개발 DB는 변경하지 않았다.

- 표준 로그아웃: 세션·SecurityContext·CSRF 정리, 쿠키 즉시 만료, 본문·리다이렉트 없는 204, 익명·정지 회원의 유효한 로그아웃
- CSRF·세션: 누락·오류·다른 세션 토큰은 403이며 정상 세션 유지, GET 로그아웃 미실행, 종료 후 이전 쿠키·토큰 거부, 새 익명 CSRF 재발급
- 상태·권한: 로그인 후 DB 정지·삭제와 관리자/고객 역할 변경이 다음 요청에 반영됨, 예상하지 못한 principal 차단, 갱신된 세션 principal의 해시·credentials 없음
- 동시 종료: 회원 조회 중 세션을 무효화해도 인증 세션을 새로 만들지 않으며 다음 요청은 401
- 실제 만료: 기본 1800초 설정을 확인하고 테스트에서 만든 한 실제 Tomcat 세션만 1초로 줄여 유휴 만료·과거 CSRF 폐기를 검증; 운영 설정 유지
- 기기·환경: 다른 기기의 인증 세션 유지, 위조 쿠키 거부, 실제 prod 프로필의 발급·만료 쿠키 이름·Path·Domain·Secure·HttpOnly·SameSite 일치
- 기존 회원가입·로그인·관리자 API·CORS 테스트도 함께 통과

표준 동작은 [Spring Security 로그아웃 문서](https://docs.spring.io/spring-security/reference/servlet/authentication/logout.html)와 [세션 저장 문서](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html)를 기준으로 한다.
