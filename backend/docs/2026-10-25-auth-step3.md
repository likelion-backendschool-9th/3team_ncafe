# 인증 3단계 — 로그인·현재 회원 조회

작성일: 2026-10-25 · 작업 브랜치: `feature/session-auth-step3` · PR 대상: `feature/session-auth`

## 구현 범위

표준 로그인 필터로 이메일·비밀번호를 검증하고, 서버 세션에 저장한 인증을 다음 HTTP 요청에서 복원한다. 현재 회원 조회는 세션 principal의 ID로 DB를 다시 조회한다. 로그아웃과 모든 보호 요청에서의 최신 회원 상태·권한 검사는 4단계에서 구현한다.

| 구성 | 담당 |
| --- | --- |
| `DatabaseUserDetailsService` | 이메일 정규화, 회원 조회, 인증 전용 principal 생성 |
| `SessionUserDetails` | 회원 ID·공개 정보·권한·활성 상태, 인증 후 자격 증명 삭제 |
| `DaoAuthenticationProvider` | 가입과 같은 비밀번호 인코더로 해시 검증, 정지 계정 거부 |
| `UsernamePasswordAuthenticationFilter` | 로그인 요청 추출, 인증, 세션 ID 변경·CSRF 폐기·SecurityContext 저장 |
| `LoginSuccessHandler`, `SecurityErrorHandler` | 리다이렉트 없는 JSON 성공·실패 응답 |
| `controller/my/UsersController`, `service/my/UsersService` | 인증된 회원 ID로 본인 정보 조회 |

2단계의 임시 인증 거부 매니저를 DB 인증으로 교체했다. `Passwords`를 통해 기존 비밀번호 제한과 손상된 해시의 안전한 실패를 로그인에도 적용한다. 계정이 없거나 이메일 입력이 잘못된 경우에도 인증 실패로 처리하며, 기본 계정을 생성하지 않는다.

## 호출 순서

1. `GET /api/v1/auth/csrf`로 익명 세션 쿠키와 CSRF 토큰을 받는다.
2. 같은 쿠키와 `X-CSRF-TOKEN` 헤더로 `POST /api/v1/auth/login`을 요청한다. 본문 형식은 **`application/x-www-form-urlencoded`**이며 필드 이름은 `email`, `password`다.
3. 성공하면 `200 {id,name,email,role,status}`와 변경된 세션 ID의 쿠키를 받는다. 비밀번호의 앞뒤 공백은 유지하고 이메일만 기존 가입 정책대로 정규화한다.
4. 로그인 전 CSRF 토큰은 폐기되므로 같은 세션으로 `GET /api/v1/auth/csrf`를 다시 호출한다. 이후 변경 요청에는 새 토큰을 사용한다.
5. `GET /api/v1/my`에 로그인 세션 쿠키를 전달하면 본인의 최신 공개 정보 5개 필드를 받는다. 다른 회원의 ID를 요청 파라미터로 선택할 수 없다.

브라우저에서 직접 호출할 때는 `credentials: "include"`를 사용한다. 폼 인코딩은 `URLSearchParams({email, password})`로 만들 수 있다. 회원가입은 기존처럼 JSON 요청이며 자동 로그인하지 않는다.

| 상황 | 응답 |
| --- | --- |
| 정상 로그인 | `200`, 공개 회원 정보와 변경된 세션 쿠키 |
| 없는 이메일·틀린 비밀번호·정지 계정 | 동일한 `401 LOGIN_FAILED`, `이메일 또는 비밀번호를 확인해 주세요.` |
| 비밀번호 제한 위반·지원하지 않거나 손상된 저장 해시 | `401 LOGIN_FAILED` |
| 로그인 요청의 CSRF 누락·불일치·다른 세션 토큰 | `403 CSRF_INVALID`, 인증하지 않음 |
| 비로그인·로그인 이전의 세션 ID로 현재 회원 조회 | `401 UNAUTHENTICATED` |
| 고객·관리자가 본인 정보 조회 | `200`, 각각 본인의 정보 |
| 고객이 관리자 API 조회 | `403 FORBIDDEN` |

로그인 성공·실패와 현재 회원 응답은 `Cache-Control: no-store`를 사용한다. 기본 로그인 HTML, `302` 이동, Basic 인증 팝업을 사용하지 않는다.

## 세션과 자격 증명

`ProviderManager`의 자격 증명 삭제를 유지하고, principal이 `CredentialsContainer`를 구현해 인증 성공 후 해시를 지운다. 해시 필드는 직렬화 대상에서도 제외한다. JPA Entity나 비밀번호 원문을 세션 principal에 넣지 않는다. 응답에는 전용 `MemberResponse`만 사용한다.

표준 필터에 연결된 세션 인증 전략과 SecurityContext 저장소가 세션 ID 변경, 인증 후 CSRF 폐기, 세션 인증 저장을 수행한다. Controller에서 별도로 인증을 만들거나 세션에 회원 ID를 중복 저장하지 않는다. CSRF 마스킹 값은 요청마다 달라질 수 있으므로 문자열 비교만으로 토큰 폐기를 판단하지 않는다.

구현 기준은 [Spring Security 로그인 문서](https://docs.spring.io/spring-security/reference/servlet/authentication/passwords/form.html), [세션 저장 문서](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html), [CSRF 문서](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)다.

## 검증

`cd backend && ./gradlew check` 통과: 단위·Security 테스트 **150개**, PostgreSQL·실제 HTTP 통합 테스트 **39개**, 총 **189개**. 실패·오류·생략 없음. 실제 개발 DB를 사용하지 않고 기존 PostgreSQL Testcontainers 격리 설정을 유지했다.

- principal·사용자 조회: 이메일 정규화, 역할 매핑·정지 상태, 조회마다 독립 principal 생성, 해시 JSON·문자열·Java 직렬화 비노출
- 실제 필터: 로그인 성공 후 저장된 SecurityContext와 다음 요청 복원, 원문 credentials와 principal 해시 삭제, 전체 세션 직렬화에도 비밀번호·해시 없음
- 실제 HTTP: 가입 후 별도 로그인, 이메일 정규화·비밀번호 공백 보존, 쿠키의 세션 ID 변경, 이전 세션 ID 재사용 거부
- CSRF: 로그인 전 토큰을 새 세션 쿠키로 재전송하면 403, 새 토큰 조회 후 정상 요청, 누락·가짜·다른 세션 토큰의 인증 차단
- 본인 정보: 고객·관리자 모두 조회 가능, DB 이름 변경 반영, 다른 회원 ID 쿼리로 본인 변경 불가
- 실패·권한: 없는 회원·잘못된 비밀번호·정지 회원의 동일 401, 입력 제한·손상/지원 불가 해시도 500 없이 401, 고객 관리자 접근 403과 실제 관리자 접근 200
- 회귀: 기존 가입·동시 가입·관리자 API·CORS·운영 Secure 쿠키 검사 유지, HTML Accept에도 기본 로그인 화면·리다이렉트 없음

## 다음 단계

4단계는 표준 로그아웃, 쿠키 만료, 기존 세션의 최신 회원 상태·역할 검사와 세션 만료 검증이다. 3단계에서는 로그인 시 정지 계정을 거부하며 로그인 후 정지·역할 변경을 모든 보호 요청에 반영하는 필터는 추가하지 않는다.
