# 관리자 취소 사유 입력·회원 조회 연동 계획

## 1. 목표와 현재 단계

**관리자가 주문 취소 사유를 작성해 취소하고, 해당 주문의 회원이 내 주문 목록·상세에서 실제 저장된 사유를 확인한다.** 2026-10-27 사용자 요청에 따른 후속 계획이다. 계획 작성 이후 사용자 구현 지시에 따라 **DB·API·관리자/회원 화면 연결을 구현했다.** 실제 검증 결과는 11장에 기록한다.

기존 DB 설계와 2026-10-26 구현에는 “사유 없이 관리자 취소”가 적용됐다. 반면 이전 프론트 커밋 `82497e5`에는 관리자 입력과 회원 표시가 있었다. 이번 요청은 이 불일치를 해소하고 **취소 사유를 실제 DB/API까지 연결해 복원**하는 요구다. 기존 문서의 “사유 없음”을 근거로 다시 제외하지 않는다.

- 브랜치: 기존 `feature/admin-orders`만 사용한다. `develop` 직접 수정·커밋·푸시와 PR 머지는 하지 않는다.
- 기준: 최신 `origin/develop` **`1eb12a3`**. 기존 PR #82는 `b897d26`으로 머지됐으므로 후속 문서/구현 PR에 예전 커밋을 중복 제안하지 않는다.
- 로컬 `develop`의 시작 위치 `62c139a7b6326caff606861b218bb1c846f943fa`는 유지한다.
- 최초 계획 PR은 문서 2개만 변경했다. 후속 구현은 아래 명시한 Order/DTO·관리자·회원 표시와 테스트·SQL/계약 문서 범위로 진행한다. 개발 DB와 환경파일은 변경하지 않는다.

기준 문서: [AGENTS.md](../../../AGENTS.md), [프론트 규칙](../../FRONTEND.md) 2·5·8·9장, [DB 설계](../../database-design.md), [백엔드 청사진](../../../backend/docs/2026-10-20-backend-blueprint.md), [관리자 API 계약](2026-10-26-backend-order-management.md), [기존 프론트 계획·결과](2026-10-26-frontend-order-management.md). 이 문서는 취소 사유에 관한 후속 변경 계획이며, 과거 실행 결과를 새 기능의 완료 근거로 쓰지 않는다.

## 3. 사용할 API와 사용자 흐름

| 화면/동작 | 주 컨트롤러 | API |
| --- | --- | --- |
| 관리자 주문 목록·상세 | `admin/OrdersController` | 기존 `GET /api/v1/admin/orders`, `GET /api/v1/admin/orders/{id}` |
| 관리자 취소 | 같은 컨트롤러 | 기존 `PUT /api/v1/admin/orders/status` |
| 회원 내 주문 목록·상세 | `my/OrdersController` | 기존 `GET /api/v1/orders`, `GET /api/v1/orders/{id}` |

별도 취소·사유 조회·사유 수정 API를 만들지 않는다. 관리자와 회원은 **동일한 DB 주문**의 사유를 조회한다.

1. 관리자가 목록 또는 상세의 취소 버튼을 누른다. 버튼 노출은 기존 서버 `allowedStatuses`를 따른다.
2. dialog에 고객에게 전달될 사유를 입력하고 취소를 확정한다. 빈 사유로는 취소되지 않는다.
3. 서버가 관리자 권한·CSRF·접수 상태·예상 상태/버전·사유를 검증하고, 상태와 사유를 한 트랜잭션으로 저장한다.
4. 관리자 상세에 저장된 사유를 표시한다. 기존 목록의 취소 섹션 이동/페이지 보정도 유지한다.
5. 해당 회원이 내 주문 목록·상세를 새로 조회하면 취소 상태와 같은 사유를 확인한다. 다른 회원에게는 노출하지 않는다.

기존 `received → canceled`와 인접 단계 이동 규칙은 유지한다. 준비 중 주문 취소, 고객 직접 취소, 취소 후 복구나 사유 편집은 이번 범위에 포함하지 않는다.

## 4. 취소 사유 계약

기존 프론트 `MAX_CANCEL_REASON_LENGTH = 200`의 사용성을 이어받아 **필수·최대 200자**를 기준으로 계획한다.

| 항목 | 규칙 |
| --- | --- |
| 이름 | JSON/프론트 `cancelReason`, DB `cancel_reason` |
| 취소 요청 | 문자열 필수. 누락·null·빈 값·공백/줄바꿈만 있는 값은 400 |
| 길이 | 입력 원문은 200자 이내. Java `String.length()`·JS `length`/`maxLength`와 같은 UTF-16 단위로 검사한다. 이모지는 보통 2단위다 |
| 저장 | 양끝 공백을 제거한다. 본문의 줄바꿈은 LF로 통일하고 문구를 보존하며 임의 기본 사유를 넣지 않는다. 저장할 수 없는 NUL 문자는 거부한다 |
| 일반 상태 변경 | 필드 생략 또는 null/빈 값만 허용한다. 비어 있지 않은 사유가 함께 오면 400으로 거부해 취소 사유로 오저장하지 않는다 |
| 조회 응답 | 관리자·회원 주문 응답에 `cancelReason: string \| null` 추가. 응답 검증에서 누락과 명시적 null을 구분한다 |
| 비취소 주문 | `cancelReason`은 null |
| 과거 취소 주문 | 저장된 사유가 없으면 null 유지. 화면에 “등록된 취소 사유가 없습니다” 안내. 사유를 추측하거나 일괄 생성하지 않는다 |
| 표시 | React 텍스트로 출력하고 `white-space: pre-wrap`·긴 문자열 줄바꿈을 사용한다. HTML로 해석하지 않는다 |

취소 요청 예시:

```json
{
  "id": 123,
  "expectedStatus": "received",
  "statusVersion": 0,
  "nextStatus": "canceled",
  "cancelReason": "주문하신 메뉴의 재료가 소진되어 취소했습니다."
}
```

일반 상태 변경의 기존 네 필드는 유지하며 `cancelReason`을 보내지 않는다. 관리자/회원 GET의 기존 필드·타입은 그대로 두고 사유만 추가한다. 고객 응답에 관리자용 `allowedStatuses`·`statusVersion`·타 회원 정보를 섞지 않는다.

## 5. 백엔드·DB 변경 계획

### 저장과 이전 데이터

- 공유 `Order`에 nullable `cancel_reason`(varchar 200)을 추가한다. 기존 생성 팩토리·멱등성 키/지문·회원 ID·품목 스냅샷 계약은 유지한다. 새 주문의 사유는 null이다.
- 현재 프로젝트는 Hibernate `ddl-auto=update`를 사용한다. 기존 DB용 nullable 컬럼 추가 SQL/적용 안내도 함께 준비하고, 기존 취소 주문이 있는 임시 DB로 검증한다. 사유 없음→NOT NULL 강제나 기존 데이터 초기화는 하지 않는다.
- 새 CHECK를 추가할 경우 비취소 주문의 사유 저장은 막되, 과거 취소 주문의 null은 허용한다. 새 취소의 사유 필수 규칙은 서버 검증/도메인에서 강제한다. Hibernate만으로 기존 제약이 자동 갱신된다고 가정하지 않는다.
- [컬럼 추가 SQL](../../../backend/docs/sql/2026-10-27-order-cancellation-reason.sql)을 준비했다. 기존 데이터가 있는 별도 임시 DB에서만 적용·재적용·재시작 검증했다. 개발 `.env`·DB는 수정/초기화하지 않으며 실제 배포 DB의 적용은 별도다.

### 상태 변경과 조회

- `ChangeOrderStatusRequest`에 선택 필드 `cancelReason`을 추가하고 원문 길이 검증을 둔다. 조건부 필수 여부와 정규화는 서비스/도메인에서도 검사한다. HTTP 검증을 우회한 직접 도메인 호출도 빈 사유로 취소되지 않아야 한다.
- `Order.changeStatus`는 기존 예상 상태·버전·허용 전이를 먼저 확인하고, 사유 검증을 마친 뒤 상태/사유를 함께 변경한다. 실패 시 두 값과 버전이 모두 유지된다.
- 취소 사유 오류는 관리자 주문 전용 예외/advice에 400 오류(`INVALID_INPUT`)를 추가하는 방식으로 처리한다. Bean Validation의 `VALIDATION_ERROR`도 프론트에서 표시한다. 일반 예외로 흘러 500이 되지 않도록 한다.
- 기존 `@Version`·`flush()`를 유지한다. 동시 취소에서는 먼저 성공한 사유만 저장되고, 409로 실패한 요청이 덮어쓰지 못한다.
- `AdminOrderResponse.from`과 고객 `OrderResponse.from`에 같은 엔티티의 사유를 매핑한다. 목록/상세 모두 같은 매핑을 사용한다. 관리자 DTO로 고객 DTO를 교체하지 않는다.
- 고객 서비스의 `findByIdAndCustomerId`·회원별 목록 조회를 유지한다. 본문/쿼리로 받은 `customerId`를 신뢰하지 않는다. 다른 회원의 상세는 기존처럼 404다.
- 주문 생성 POST의 입력·가격 검증·장바구니 삭제·멱등성 지문은 바꾸지 않는다. 응답 DTO를 공유하므로 생성 응답에는 null이 추가되고, 같은 키 재조회에는 DB의 현재 값이 반영될 수 있음을 회귀 확인한다.

| --- | --- |
| 관리자 `_lib/types.ts`·`_lib/api.ts` | 요청의 선택 사유, 응답의 nullable 사유 검증, 폼 오류/입력값 타입 확장. 현재 공통 요청기 재사용 |
| 관리자 `_actions.ts` | 첫 단계 관리자 권한 검사, 사유 검증, 취소일 때만 JSON에 사유 포함, 400 입력 복구와 기존 401/403/404/409 처리 유지 |
| `StatusChangeForm` | 주문 ID/버전에 귀속된 입력 상태·pending·서버 오류를 dialog에 전달. 일반 상태 select 동작 유지 |
| `ConfirmCancelDialog` | 사유 textarea·보이는 label·필수/200자 안내·문자 수·확인/닫기. 고객에게 전달되는 문구임을 표시 |
| 관리자 상세 `OrderMeta` | 기존 상세 구조 안에서 저장된 “주문 취소 사유”와 과거 null 안내 표시. 목록 dialog에서 입력해도 상세에 같은 값 표시 |
| 고객 `_lib/types.ts`·`_lib/api.ts` | 기존 `CustomerOrderResponse`·`parseCustomerOrder`에 사유만 추가. GET/숫자 ID/현재 요청기 유지 |
| 고객 `_components/OrderCancelReason.tsx` (신규 예정) | 내 목록과 상세가 함께 사용하는 읽기 전용 서버 컴포넌트. 사유/과거 null 안내·줄바꿈 표시 |
| 고객 `page.tsx`·`[id]/page.tsx` | 취소 상태에서 위 컴포넌트 조립. 기존 `h1`, 최근 100건 안내, 상세 숫자 ID·본인 조회·접수 flash 유지 |
| 각 라우트 CSS Modules | textarea·오류·사유 문구 스타일만 추가. 기존 디자인·모바일 레이아웃 유지 |

- 기본은 서버 컴포넌트다. 입력·dialog·pending만 기존 client 경계에 둔다. 다른 라우트의 private 컴포넌트를 import하거나 도메인용 전역 상태를 만들지 않는다.
- 관리자 목록·상세에 이미 쓰이는 하나의 취소 dialog를 확장한다. 회원 화면에 별도 취소 폼이나 회원용 취소 액션은 추가하지 않는다.
- 현재 dialog의 Tab 처리는 **버튼만** 수집한다. textarea를 추가할 때 포커스 순환 대상도 함께 수정해야 한다. 초기/검증 오류 포커스는 사유 입력 칸, Esc/닫기 후에는 원래 버튼으로 복귀한다.
- 입력 실패/400/CSRF/5xx에는 dialog와 입력을 유지하고 오류를 연결한다. 닫기·주문/버전 변경 시 초안을 초기화한다. 409는 최신 서버 값으로 다시 보여 주며 오래된 초안을 자동 제출하지 않는다.
- pending 동안 입력/확인 중복 제출을 막는다. 사유가 고객에게 표시되는 내용임을 안내하고, label·`aria-invalid`·`aria-describedby`·상태 알림을 유지한다.
- 성공 후 기존 관리자/고객 목록·해당 상세 경로를 재검증한다. **경로 재검증이 다른 회원 브라우저에 즉시 푸시하는 기능은 아니다.** 회원은 상세 진입·새로고침·기존 탭 복귀 조회에서 최신 사유를 확인한다. 새 폴링·알림은 추가하지 않는다.

| A 인증 | 공통 요청기·requireRole·CSRF를 재사용하고 기존 회귀 실행. 이번 요구만으로 `client.ts`·`backend-session.ts`·`proxy.ts`·`SecurityConfig`를 변경할 계획은 없음 |

| 공통 문서 | 구현 시 DB 설계·백엔드 청사진·관리자 계약·FRONTEND의 취소 관련 문구만 갱신. 다른 담당 진행 현황을 덮어쓰지 않음 |

필요한 파일은 위 표에 먼저 공개하고 같은 브랜치에서 변경한다. 다른 사람 브랜치를 수정하지 않으며, 착수 직전 최신 develop과 열려 있는 주문 관련 PR을 다시 대조한다. 리팩터링·공통 인증 방식 변경·장바구니·체크아웃 개편·관리자 홈 집계·실제 결제는 끼워 넣지 않는다.

현재 문서에 남은 “사유 없음”은 **현재 구현/과거 결과**이고, 이 계획의 요구와는 다르다. 구현 단계에서는 다음을 함께 갱신해 문서와 코드가 다시 어긋나지 않게 한다.

- `docs/database-design.md`: 주문 컬럼·관리자 취소/고객 표시 규칙.
- `backend/docs/2026-10-20-backend-blueprint.md`: 기존 `/status` 요청 필드와 취소 사유 계약.
- `docs/admin/orders/2026-10-26-backend-order-management.md`·기존 프론트 계획: 새 계약 링크와 현재 동작. 과거 검증 기록은 날짜를 남겨 구분.

백엔드 응답의 추가 필드는 기존 클라이언트가 무시할 수 있지만, **사유 없는 관리자 취소는 새 계약에서 400**이다. 관리자 새 UI와 서버 적용 순서를 함께 검토한다. DB 컬럼을 먼저 준비하고 서버→프론트를 같은 릴리스에 적용해, 새 프론트가 필드 없는 옛 응답을 받거나 옛 UI가 사유 없이 취소하는 기간을 최소화한다. 이를 피하려고 새 취소의 사유 필수 규칙을 약하게 만들지는 않는다.

각 단계는 타입/테스트가 통과하는 논리적 단위로 커밋한다. PR에는 공유 파일·회원 화면 변경과 D/DB 리뷰 대상을 명시한다. 계획 PR을 머지해도 기능 구현 완료를 의미하지 않는다.

## 11. 구현 결과와 실제 검증 (2026-10-27)

### 구현한 연결

- `Order.cancelReason`과 조건부 검증을 추가하고, 관리자 변경 요청·관리자/고객 응답에 사유를 연결했다. 이전 취소 행의 null을 허용하는 컬럼/제약 SQL도 제공한다.
- 상태·사유·버전은 기존 트랜잭션/낙관적 잠금으로 함께 저장한다. 사유 누락·공백·초과 길이·NUL·비취소 변경의 사유 입력은 400이며, 실패 전에 엔티티 필드를 변경하지 않는다.
- 관리자 목록/상세의 같은 dialog에 textarea·200자 안내·입력 복구·pending·Tab/Shift+Tab/Esc 처리를 추가했다. HTML FormData의 CRLF는 textarea의 LF 기준으로 통일한 뒤 길이를 검사하고, 서버도 저장 개행을 LF로 통일한다.
- 관리자 상세와 회원 목록/상세에 저장된 사유를 표시한다. 회원 표시는 지역 서버 컴포넌트를 재사용하고 긴 문구/개행은 줄바꿈한다. 사유 없는 과거 취소 주문은 안내 문구를 보여 준다.
- 고객 직접 취소는 추가하지 않았다. 주문 생성·멱등성·본인 조회, 현재 apiFetch/csrfHeaders/requireRole, 공통 Proxy·SecurityConfig는 유지했다.

### 배포와 리뷰 범위

- 기존 DB에서는 [nullable 컬럼/제약 SQL](../../../backend/docs/sql/2026-10-27-order-cancellation-reason.sql)을 대상 DB/스키마에 적용한 뒤 서버와 관리자/회원 프론트를 함께 배포한다. 개발/운영 DB에 이 SQL을 대신 실행한 것은 아니다.
- 사유 없는 과거 행을 지우거나 사유를 생성하지 않는다. 새 관리자 취소는 사유 없는 옛 UI 요청을 400으로 거부한다.
- D 리뷰: 공유 Order·고객 OrderResponse·회원 응답 검증/표시. DB 리뷰: nullable 필드·기존 행·CHECK·적용 순서. A 영역의 공통 인증/요청기/권한 설정은 수정하지 않았다.
